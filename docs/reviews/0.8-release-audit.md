# Create 0.8 release audit

The behavior reference is Java Create 6.0.10 on Minecraft 1.21.1. The development
client uses Horizon Nightly `2ebf00a` plus the three patches listed in
[Validation](../../VALIDATION.md). Earlier evidence is retained there alongside
the checks for this audit.

## Chunk ownership

The source cells, landing cells and persisted moving record share a loaded
16×16 chunk column in the current adapter. The column spans the world's height.
Mechanical and Windmill Bearings accept up to 2,048 eligible plain blocks and
require every snapped pose to fit. Other bearing cargo and most drivers have
a 64-block bound. A Clockwork Bearing uses one record per hand, with a common
limit of four records in the column. Piston heads and poles count against the
piston's bound, and the Gantry Carriage leaves room for up to 63 cargo blocks.
An oblique rotary pose can enter a loaded neighbor while the source and all
snapped positions stay in the owner column.

Java's default maximum is 2,048 blocks for its normal contraption search. The
limit is configurable and Java checks that the affected positions are loaded.
It does not require them to share a column.

[The region-boundary fixture](../../tools/contraption_column_boundary_checks.py)
separates capture with source cells in two regions from capture where only a
snapped landing would enter the other region. Both are valid in Java. Horizon
refuses them before altering the source. The fixture checks both saved columns
after a cold restart.

Horizon currently queues each changed chunk as a separate record. Waiting for
those records to save does not make them a transaction. Extending the adapter
requires a durable operation covering the moving record, all edited columns,
and their inventory and glue changes. Recovery must finish or roll back the
operation before the world streams either side. Test crashes between writes
and after the final write, as well as unload and restart, across an Anvil region
boundary. Keep reading old single-column records.

## Release gate

1. Re-run the audit fixtures on the candidate build. Keep the build receipt
   with the Java and Horizon results and the manual review world.
2. Once the upstream state-dependent light declaration is available, build
   the registry artifact on the official Nightly that contains it and verify
   a fresh Launcher install. Exercise original local JAR resources and the
   bundled resources separately.
3. Compare the installed artifact with the candidate. Run a cold world reload
   and the affected behavior and settings checks before submitting the update.
